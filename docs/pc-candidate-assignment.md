今回の完了出力は `captures/labeling/candidate-assignment-20261027-v3/`（Git管理外）。v1はsources JARも検索対象になったためコンパイル前に失敗した空フォルダ。v2は初回の評価、v3は入力ハッシュの前後照合等を加えた最終評価で、数値はv2と一致する。既存出力先へ上書きしない。再実行には必ず新しい出力先を使う。

- `classes/`: PC専用のコンパイル結果。現在のKotlinソースから別に作り、Androidのビルド成果物を参照・更新しない。

## 方式と仮定

1. 現在の `BoardGeometry.kt`・`StoneClassifier.kt` をPC専用フォルダへコンパイルする。Java2Dの長辺2048・bilinear縮小を使う。現行判定を再実行し、3枚とも保存済みの予測全361点と混同行列が一致しなければ中止する。AndroidのImageDecoderとの完全一致を意味しない。
2. 交点ごとに候補を独立に選ぶ前に、四隅の射影内を交点間隔0.2刻み（91×91位置）で調べる。既存Kotlinの木地参照・色処理・画素数条件を共有する。木地参照が得られなければ中止する。四隅の外は探索・補完せず、端の制約が残る。
3. 黒白の色支持率が高い位置から半径0.65未満の点をまとめる（NMS）。同率なら画像の上・左を優先する。連鎖的な結合はせず、代表点と抑制した全支持点を保存する。異色が同じ範囲にあれば未割当とする。代表点は色の支持位置であり、輪郭から求めた上面の中心ではない。同率時の偏りも残る。
4. `zero` は移動量0の対照条件。`manual` は本人指定の見かけ中心を逆射影し、本来の交点との差のx/yそれぞれの中央値を写真ごとに求め、候補から引く。低角度は約(-0.117, -0.764)、高い位置は約(-0.106, -0.410)交点間隔。上方には中心指定がないため0のままで、manualでもzeroと同じ結果になる。これは**奥側4石の手動の対応情報を使う校正**であり、自動で撮影姿勢や石高を推定した方式ではない。
5. 補正後の全候補と361交点を比較し、距離0.55以内かつ最近傍と次点の距離差0.15以上の場合だけ提案する。同じ交点への複数候補や曖昧候補との競合は、勝者を選ばず未割当とする。一候補は高々一交点、一交点は高々一候補。第二候補への押し込みや盤全体の最適化は行わない。
6. 石が割り当たらない交点は、校正した予想上面位置で既存の色処理が空を支持し、補正後の候補が0.8未満に存在しない場合のみ空とする。それ以外は不明。射影範囲外の位置も不明。この空の根拠は位置ずれモデルが正しいことに依存し、モデルを誤ると石を空と誤ることもある。

推論へ渡すのは画像、四隅、明示した校正値だけ。GTの空黒白・石数は候補抽出・抑制・対応先選択・コストに渡さず、予測が完成した後に比較する。手動中心の対象行列は校正に使うため、校正4石の回復を独立した成功例として数えない。色判定の閾値と今回の幾何パラメータは比較結果を見て調整していない。

同じ候補の二重割当は防ぐが、NMSは輪郭や物体IDを使わない近似である。一つの石が離れた複数の色支持領域を生む場合の分割、接近した別の石の統合を完全には防げない。候補数を真の石数と扱わない。
