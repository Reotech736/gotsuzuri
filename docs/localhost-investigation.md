# localhost接続切断の調査（2026-11-07）

本人の依頼で、GT画面の読み込み・保存応答で断続的に出る接続切断を調査した。結論は、**アプリ固有のGT処理から切り離して再現でき、応答直後にHTTPサーバーが接続を閉じる条件への依存を確認した**。切断を発生させているOS内の部品や、実行環境の影響までは特定していない。GTサーバーの接続方式はこの調査では変更していない。

## 確認した事実

- GTサーバーは待受を継続し、停止・再起動していなかった。現在の応答処理はHTTP/1.1でも各応答にConnection: closeを付け、応答後に閉じる。
- Python標準ライブラリだけの一時HTTPサーバーでも、人工データ1KBのGETでWinError 10054を再現した。urllib、http.client、生ソケットのクライアントで失敗した。大きな写真、JSONのラベル、Origin・トークン・更新番号を扱わなくても発生する。
- Node.js標準HTTPサーバーと標準HTTPクライアントでもECONNRESETを再現した。ブラウザ、Python、碁つづり固有の処理だけで説明できる問題ではない。
- Windowsのユーザープロキシは無効、ProxyServer・自動設定URLなし、プロキシ環境変数なしだった。これで全てのフィルターや実行環境の介在を否定したことにはならない。
- Winsockの読み取り一覧は標準プロバイダーだった。特定の保護製品・VPNのせいだと断定する材料は得られていない。保護機能・VPN・ファイアウォール・システム設定は変更していない。
- PktMonの状態取得はOSのアクセス拒否となり、パケット／ETWによる発生元の特定は行えていない。管理者昇格のUIも起動していない。

## 接続終了条件の比較

同じNode.jsプロセス内で、127.0.0.1だけに待ち受ける一時サーバーを起動し、同じ1MBの人工データを条件ごと50回転送した。本文のバイト数とSHA-256が一致して初めて成功とする。時間上限は1要求1.5秒。

| 条件 | 本文受信成功 | 失敗 |
| --- | ---: | ---: |
| 生TCP、規定の本文を受け取った時点で確認 | 50/50 | 0 |
| HTTP、応答直後にサーバーからclose | 37/50 | 13（ECONNRESET） |
| HTTP、keep-alive、毎回新しい接続 | 50/50 | 0 |
| HTTP、keep-alive、接続を再利用 | 50/50 | 0 |

一つ前の50回比較でもcloseは41/50、keep-aliveは50/50。新規接続でもkeep-alive条件は成功したため、接続再利用の有無だけでは差を説明できない。サーバーの送信完了コールバックは失敗した条件でも呼ばれたが、これは相手の本文受信完了の保証ではない。失敗時は本文の一部を受け取った後、8〜10ms程度でリセットされた。

Pythonの小規模比較でも、標準の応答後closeは29/30、ヘッダーと本文をまとめた送信は29/30、shutdownを呼ばずcloseだけにした場合28/30。keep-aliveと30msのclose遅延では30/30だった。試行数は少なく、遅延を本体へ入れる根拠とはしない。Pythonの標準終了処理はshutdown(SHUT_WR)を呼んでおり、単純な「shutdownが抜けている」説明も当たらない。

最初の生TCP診断の一部は本文後のEOFまで待っており、本文が全て届いた後のタイムアウトも失敗に含んでいた。最終比較では本文の全バイト・ハッシュ確認へ基準を合わせた。これらの初期値と最終表を混在させない。HTTPの本文途中でのリセットはこの基準修正後も再現した。

この結果は接続終了タイミングに依存する問題を示すが、keep-aliveでの無失敗を将来の安定性保証とはしない。RSTを作った部品や、その理由を特定するには、別の起動環境での再現比較・必要に応じた権限のある通信トレースが残る。現時点でWindows全般、特定製品、Codexのいずれかを原因と確定しない。

## 再現用スクリプト

`scripts/diagnostics/localhost-probe.cjs` はNode.js標準モジュールだけで実行できる。外部送信・GT読み書き・設定変更をせず、127.0.0.1の一時ポートで人工データを使う。各転送は時間上限付きで、最後に一時サーバーを終了する。結果はcaptures/diagnosticsの新しいファイルへ出力し、既存ファイルへ上書きしない。

通常のPowerShellでリポジトリ直下から実行すると、Codexから起動した場合と比較できる。別の起動元でも必ず違う経路になると保証するものではないが、実行環境への依存を調べる次の切り分けになる。

```powershell
node .\scripts\diagnostics\localhost-probe.cjs
```

今回の最終比較を再実行する場合：

```powershell
node .\scripts\diagnostics\localhost-probe.cjs --attempts 50 --sizes 1048576
```

生の結果は `captures/diagnostics/localhost-20261107/` に保存した。最終条件は `teardown-fresh-50-result.json`、前段の比較は `teardown-50-result.json`、Pythonの最小再現は `synthetic-http-result.json`、その他はファイル名ごとに区別する。診断用の個人環境記録はGitへ追加しない。再現スクリプトはJS構文確認と上記の実行で検証した。ここで「失敗」は診断対象の通信結果で、スクリプトが全件成功を報告したという意味ではない。

保存IDによる確認・再送とJSON退避は維持する。keep-aliveは有力な改善候補だが、GT保存APIを含む別サーバーでの検証が必要。本人が編集している可能性があるGTサーバーを調査のために再起動しない。今回の配置B上方は準備・表示確認済みで、本人の分類は待ちの状態。

## 仕様上の意味

localhostでもTCPはプロセスとOSの通信処理を経由する。WinError 10054は、確立済み接続がリセットされたというWinsockの通知であり、インターネット回線の障害やアプリのクラッシュまで示すものではない。[Microsoftのエラー定義](https://learn.microsoft.com/en-us/windows/win32/winsock/windows-sockets-error-codes-2) を参照する。

送信側のcloseと受信完了は同じ出来事ではなく、通常の終了と強制終了も区別される。今回の観測と一般的な仕組みを混同せず、原因の確定には追加の証拠を使う。[Microsoftのソケット終了手順](https://learn.microsoft.com/en-us/windows/win32/winsock/graceful-shutdown-linger-options-and-socket-closure-2) を参照する。
