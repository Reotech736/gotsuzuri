- Windowsのユーザープロキシは無効、ProxyServer・自動設定URLなし、プロキシ環境変数なしだった。これで全てのフィルターや実行環境の介在を否定したことにはならない。

同じNode.jsプロセス内で、127.0.0.1だけに待ち受ける一時サーバーを起動し、同じ1MBの人工データを条件ごと50回転送した。本文のバイト数とSHA-256が一致して初めて成功とする。時間上限は1要求1.5秒。

| 条件 | 本文受信成功 | 失敗 |
| --- | ---: | ---: |
| 生TCP、規定の本文を受け取った時点で確認 | 50/50 | 0 |
| HTTP、応答直後にサーバーからclose | 37/50 | 13（ECONNRESET） |
| HTTP、keep-alive、毎回新しい接続 | 50/50 | 0 |

この結果は接続終了タイミングに依存する問題を示すが、keep-aliveでの無失敗を将来の安定性保証とはしない。RSTを作った部品や、その理由を特定するには、別の起動環境での再現比較・必要に応じた権限のある通信トレースが残る。現時点でWindows全般、特定製品、Codexのいずれかを原因と確定しない。

## 仕様上の意味

localhostでもTCPはプロセスとOSの通信処理を経由する。WinError 10054は、確立済み接続がリセットされたというWinsockの通知であり、インターネット回線の障害やアプリのクラッシュまで示すものではない。[Microsoftのエラー定義](https://learn.microsoft.com/en-us/windows/win32/winsock/windows-sockets-error-codes-2) を参照する。

送信側のcloseと受信完了は同じ出来事ではなく、通常の終了と強制終了も区別される。今回の観測と一般的な仕組みを混同せず、原因の確定には追加の証拠を使う。[Microsoftのソケット終了手順](https://learn.microsoft.com/en-us/windows/win32/winsock/graceful-shutdown-linger-options-and-socket-closure-2) を参照する。
